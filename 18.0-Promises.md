# JavaScript Promises — Complete Guide (Beginner to Interview Level)

---

## 1. What Is a Promise?

**Simple definition:** A Promise is a JavaScript object that represents a value which is not available yet, but will be available in the future — either successfully (with a result) or unsuccessfully (with an error).

Think of it as a placeholder for a future value.

**Why is it called a "Promise"?**
It behaves exactly like a real-life promise. When someone promises you something, there are three possible situations:
- They haven't decided yet (still waiting) → **pending**
- They kept the promise → **fulfilled**
- They broke the promise → **rejected**

JavaScript borrowed this idea directly. A Promise "promises" that some asynchronous work will finish and give you a result later.

### The Three Promise States

| State | Meaning |
|---|---|
| **Pending** | The initial state. The async operation hasn't finished yet. |
| **Fulfilled** | The operation completed successfully. `resolve(value)` was called. |
| **Rejected** | The operation failed. `reject(error)` was called. |

### State Transition Diagram

```
              resolve(value)
   ┌─────────┐ ────────────► ┌────────────┐
   │ PENDING │                │  FULFILLED │
   └─────────┘ ────────────► └────────────┘
              reject(error)
                   │
                   ▼
             ┌────────────┐
             │  REJECTED  │
             └────────────┘
```

**Important rule:** Once a Promise moves to `fulfilled` or `rejected`, it is called **settled**, and it can NEVER change state again. A Promise can only transition once — pending → fulfilled, OR pending → rejected. Never both.

> **Practice question:** If a Promise is already fulfilled, and later someone calls `reject()` on it, what happens? *(Answer: nothing — the state is locked once settled.)*

## 2. Why Do We Need Promises?

### Synchronous vs Asynchronous

**Synchronous code** runs line by line. Each line waits for the previous line to finish.

```js
console.log("1");
console.log("2");
console.log("3");
// Output: 1, 2, 3 — always in order, one at a time
```

**Asynchronous code** allows JavaScript to start a task (like a network request), NOT wait for it, and continue running other code. When the task finishes, JavaScript comes back to handle the result.

### Why does JavaScript need asynchronous behavior?

JavaScript is **single-threaded** — it can only do one thing at a time. If it waited (blocked) for every slow operation (like fetching data from a server), the entire website would freeze. Buttons wouldn't click, scrolling wouldn't work, nothing would respond.

### What happens when an API takes time to respond?

Imagine calling an API to fetch user data. That request might take 200ms, 2 seconds, or fail entirely. JavaScript cannot pause and wait — the browser tab would appear frozen the whole time.

### Why can't we just "wait" for the response?

Because waiting = blocking. Blocking the single thread means:
- The page becomes unresponsive
- No animations run
- No user clicks are processed
- The whole app feels frozen

### The Problem Before Promises: Callbacks

Before Promises, developers handled async results using **callback functions** — a function passed as an argument, to be called later when the operation finishes.

```js
getUser(function(user) {
    getOrders(user.id, function(orders) {
        getOrderDetails(orders, function(details) {
            console.log(details);
        });
    });
});
```

This works, but it becomes messy fast — this is called **callback hell**, explained next.

**Real-world example:** Imagine ordering food online. You place the order (start the async task), then you don't stand at the door staring at it — you continue watching TV (JS continues running other code). When the food arrives (response comes back), you get notified (callback/Promise resolves) and you go get it.

## 3. What Problems Do Promises Overcome?

### Problem 1: Callback Hell

When you have many async operations that depend on each other, callbacks nest deeper and deeper, forming a "pyramid of doom":

```js
// BEFORE PROMISES — Callback Hell
loginUser(username, password, function(user) {
    getProfile(user.id, function(profile) {
        getFriends(profile.id, function(friends) {
            getFriendPosts(friends, function(posts) {
                console.log(posts);
                // Deep, hard to read, hard to maintain
            }, function(err) { console.log(err); });
        }, function(err) { console.log(err); });
    }, function(err) { console.log(err); });
}, function(err) { console.log(err); });
```

### Problem 2: Difficult Error Handling

With callbacks, every single step needs its own error-handling logic (an extra error callback each time). There's no single, centralized way to catch an error from anywhere in the chain.

### Problem 3: Difficult Readability

Deep nesting makes code visually confusing. It's hard to tell what runs after what, and the logical flow gets buried in indentation.

### Problem 4: Difficult Sequential Operations

Running steps one after another, and passing results along, is clumsy and repetitive with callbacks.

### The Same Problem, Solved With Promises

```js
// AFTER PROMISES — Clean and Flat
loginUser(username, password)
    .then(user => getProfile(user.id))
    .then(profile => getFriends(profile.id))
    .then(friends => getFriendPosts(friends))
    .then(posts => console.log(posts))
    .catch(err => console.log(err)); // ONE place to catch ANY error
```

Notice: flat structure, one `.catch()` for the whole chain, and easy-to-follow top-to-bottom logic.

> **Practice question:** What is the main visual difference between callback hell and a Promise chain? *(Answer: nesting/indentation vs. flat chaining.)*

## 4. Promise Syntax

```js
const promise = new Promise((resolve, reject) => {
    // asynchronous operation

    if (success) {
        resolve(result);
    } else {
        reject(error);
    }
});
```

### Breaking Down Every Part

| Part | Meaning |
|---|---|
| `new Promise()` | Creates a new Promise object. |
| **executor function** | The function `(resolve, reject) => {...}` passed into `new Promise()`. It runs **immediately** (synchronously) when the Promise is created. |
| `resolve` | A function you call when the async operation succeeds. It moves the Promise to the **fulfilled** state and passes the result along. |
| `reject` | A function you call when the async operation fails. It moves the Promise to the **rejected** state and passes the error along. |
| **pending** | Default state, right after creation, before `resolve` or `reject` is called. |
| **fulfilled** | State after `resolve()` runs. |
| **rejected** | State after `reject()` runs. |

**Key point:** The executor function runs immediately and synchronously, but the actual async work inside it (like a `setTimeout` or network call) runs later. That's why the Promise starts in "pending."

## 5. Simple Code Example

```js
const promise = new Promise((resolve, reject) => {
    let orderReady = true; // simulate a condition

    setTimeout(() => {
        if (orderReady) {
            resolve("Your coffee is ready ☕");
        } else {
            reject("Sorry, we ran out of coffee");
        }
    }, 2000);
});
```

### Line-by-Line Explanation

1. `const promise = new Promise(...)` — We create a new Promise and store it in a variable.
2. `(resolve, reject) => {...}` — This is the executor function. JavaScript gives us two functions: `resolve` and `reject`.
3. `let orderReady = true;` — A simple flag simulating whether the task succeeded.
4. `setTimeout(() => {...}, 2000)` — Simulates an async delay of 2 seconds (like waiting for a server).
5. Inside the timeout: if `orderReady` is true, we call `resolve(...)` with a success message. Otherwise, we call `reject(...)` with an error message.
6. At this point, the Promise variable `promise` holds a "pending" Promise. It won't become fulfilled/rejected until 2 seconds pass.

> **Practice question:** What state is `promise` in immediately after this code runs, before the 2 seconds pass? *(Answer: pending.)*

## 6. Consuming a Promise

Once you have a Promise, you consume (use) it with three methods:

| Method | Runs when... |
|---|---|
| `.then()` | The Promise is **fulfilled** (success). Also can handle rejection if you pass a second argument. |
| `.catch()` | The Promise is **rejected** (failure) — anywhere in the chain above it. |
| `.finally()` | Always runs, whether fulfilled or rejected — used for cleanup (e.g., hiding a loading spinner). |

```js
promise
    .then(result => {
        console.log("Success:", result);
    })
    .catch(error => {
        console.log("Error:", error);
    })
    .finally(() => {
        console.log("This runs no matter what happened.");
    });
```

**Execution order:**
- If `resolve()` was called → `.then()` runs, `.catch()` is skipped.
- If `reject()` was called → `.then()`'s success callback is skipped, `.catch()` runs.
- `.finally()` runs in **both** cases, always last.

## 7. Promise Chaining

**Simple explanation:** Each `.then()` returns a **new Promise**. This lets you chain multiple `.then()` calls together, where each step receives the value returned by the previous step.

```js
getUser()
    .then(user => getOrders(user.id))
    .then(orders => getOrderDetails(orders))
    .then(details => console.log(details))
    .catch(error => console.log(error));
```

### How the value moves from one `.then()` to the next

1. `getUser()` returns a Promise. When it resolves, it gives us a `user` object.
2. Inside the first `.then()`, we call `getOrders(user.id)` — this itself returns a Promise. Because we `return` it, the chain "waits" for this new Promise before moving to the next `.then()`.
3. When that resolves, `orders` is passed into the second `.then()`.
4. This continues down the chain — each step's return value becomes the next step's input.
5. If ANY step in this chain throws an error or rejects, it skips directly to `.catch()`.

> **Practice question:** What would happen if you forgot to `return` the result inside a `.then()`? *(Answer: the next `.then()` would receive `undefined` instead of the actual value.)*

## 9. Real Website Example — E-commerce Product Search

**Flow:**
1. User types `iPhone` into the search box.
2. The website sends a request to the backend.
3. The server processes the request and searches the database.
4. The server sends back matching products.
5. The Promise becomes **fulfilled**.
6. `.then()` receives the products.
7. The UI displays the products.
8. If the request fails, `.catch()` displays an error message.

### Complete JavaScript Code

```js
function searchProducts(query) {
    return new Promise((resolve, reject) => {
        // Simulating a network request
        fetch(`/api/products/search?q=${encodeURIComponent(query)}`)
            .then(response => {
                if (!response.ok) {
                    throw new Error("Server error: " + response.status);
                }
                return response.json();
            })
            .then(data => resolve(data.products))
            .catch(error => reject(error));
    });
}

// Consuming the function
const searchInput = "iPhone";

searchProducts(searchInput)
    .then(products => {
        if (products.length === 0) {
            document.getElementById("results").innerText = "No products found.";
        } else {
            renderProducts(products);
        }
    })
    .catch(error => {
        document.getElementById("results").innerText = "Something went wrong: " + error.message;
    });

function renderProducts(products) {
    const container = document.getElementById("results");
    container.innerHTML = products
        .map(p => `<div class="product-card"><h3>${p.name}</h3><p>₹${p.price}</p></div>`)
        .join("");
}
```

## 10. One Strong Real-Life Analogy — The Restaurant Food Order

Imagine you go to a restaurant and place an order for pizza.

| Restaurant Analogy | Promise Concept |
|---|---|
| You place your order and get a **token number** | `new Promise()` is created |
| The kitchen is preparing your food, order not ready yet | **Pending** state |
| The waiter later brings your pizza to your table | `resolve()` is called → **Fulfilled** |
| The kitchen runs out of ingredients and cancels your order | `reject()` is called → **Rejected** |
| "When my food arrives, I will eat it" | `.then()` — runs when the order succeeds |
| "If my order is cancelled, I will ask for a refund" | `.catch()` — runs when the order fails |
| "Either way, I will leave a review afterward" | `.finally()` — runs regardless of outcome |

You don't stand at the kitchen door waiting — you sit at your table, maybe chat with friends (JavaScript keeps running other code). When your food is ready (or cancelled), you get a notification and react accordingly. That's exactly how a Promise behaves — you set up what to do "when it's ready" (`.then`) or "if it fails" (`.catch`), and JavaScript continues doing other things in the meantime.

## 11. Promise vs Callback

| Callback | Promise |
|---|---|
| Simple function passed as an argument, called later | Object representing a future value |
| Nesting causes "callback hell" | Chaining keeps code flat and readable |
| Error handling is scattered across every function | Centralized error handling with `.catch()` |
| No built-in way to run tasks in parallel easily | Built-in methods like `Promise.all()` for parallel tasks |
| Harder to reason about execution order | Predictable execution order (`.then()` chain) |
| Still used for simple, one-off async tasks (e.g., event listeners, `setTimeout`) | Preferred for anything involving multiple or dependent async steps |

**When are callbacks still useful?**
- Event listeners (`button.addEventListener('click', callback)`) — these fire repeatedly, not just once, so Promises don't fit naturally.
- Simple, single-step async operations where chaining isn't needed.
- Some older Node.js APIs still use callback style (though many now support Promises too).

**Why Promises are generally preferred:** They make multi-step async logic readable, provide centralized error handling, and offer utility methods (`all`, `race`, `any`, `allSettled`) that callbacks don't have natively.

## 12. Promise vs Async/Await

**Important:** `async/await` does **not** replace Promises. It is just **syntax sugar** built on top of Promises — a cleaner way to write and read Promise-based code. Under the hood, `async/await` still uses Promises.

### Promise-based version

```js
function getData() {
    fetchData()
        .then(data => console.log(data))
        .catch(error => console.log(error));
}
```

### Equivalent async/await version

```js
async function getData() {
    try {
        const data = await fetchData();
        console.log(data);
    } catch (error) {
        console.log(error);
    }
}
```

**Key facts:**
- An `async` function **always returns a Promise**, automatically.
- `await` pauses execution *within that function only* until the Promise settles — it does NOT block the rest of the JavaScript program.
- `try/catch` replaces `.catch()` for error handling.

> **Practice question:** Does `await` block the entire browser/program while waiting? *(Answer: No — it only pauses the async function it's inside. Everything else keeps running.)*

## 13. Promise Static Methods

### `Promise.all()`
- **What it does:** Takes an array of Promises and waits for ALL of them to resolve. If any ONE rejects, the whole thing rejects immediately.
- **When to use:** When you need multiple independent async results, and you need ALL of them to proceed (e.g., loading several sections of a dashboard).
```js
Promise.all([fetchUser(), fetchOrders(), fetchNotifications()])
    .then(([user, orders, notifications]) => {
        console.log(user, orders, notifications);
    })
    .catch(error => console.log("One of them failed:", error));
```
- **Real-world use case:** Loading a dashboard that needs profile data, orders, and notifications all at once before rendering.

### `Promise.allSettled()`
- **What it does:** Waits for ALL Promises to settle (either fulfilled or rejected), and never short-circuits. Returns an array of results with status info.
- **When to use:** When you want results from every Promise, even if some fail.
```js
Promise.allSettled([fetchUser(), fetchOrders()])
    .then(results => {
        results.forEach(r => {
            if (r.status === "fulfilled") console.log(r.value);
            else console.log("Failed:", r.reason);
        });
    });
```
- **Real-world use case:** Sending analytics events to multiple services — you want to know which succeeded and which failed, without one failure stopping the others.

### `Promise.race()`
- **What it does:** Returns as soon as the FIRST Promise settles (whether fulfilled or rejected) — ignores the rest.
- **When to use:** Timeouts, or picking whichever source responds fastest.
```js
Promise.race([fetchData(), timeout(5000)])
    .then(result => console.log(result))
    .catch(error => console.log("Too slow or failed:", error));
```
- **Real-world use case:** Setting a timeout for an API call — if the server doesn't respond within 5 seconds, show a "request timed out" error.

### `Promise.any()`
- **What it does:** Returns as soon as the FIRST Promise **fulfills** (succeeds). Ignores rejections unless ALL of them reject.
- **When to use:** When you have multiple sources and just need ONE successful result.
```js
Promise.any([fetchFromServerA(), fetchFromServerB()])
    .then(result => console.log("First success:", result))
    .catch(error => console.log("All failed:", error));
```
- **Real-world use case:** Fetching the same data from multiple CDN mirrors — use whichever responds successfully first.

### `Promise.resolve()`
- **What it does:** Creates a Promise that is immediately resolved with the given value.
- **When to use:** When you need to return a Promise but already have the value (for consistency in async functions).
```js
Promise.resolve("Already have this data").then(console.log);
```
- **Real-world use case:** Returning cached data from a function that normally makes an async call — keeps the return type consistent (always a Promise).

### `Promise.reject()`
- **What it does:** Creates a Promise that is immediately rejected with the given reason.
- **When to use:** For testing, or short-circuiting a function when you already know it should fail.
```js
Promise.reject(new Error("Invalid input")).catch(console.log);
```
- **Real-world use case:** Validating input before making an API call — reject immediately if validation fails, without hitting the server.

## 14. Important Promise Concepts

- **Promise is an object:** It's a regular JavaScript object with internal state and methods (`.then`, `.catch`, `.finally`).
- **Promise is asynchronous:** Even if `resolve()` is called immediately/synchronously inside the executor, `.then()` callbacks are ALWAYS scheduled to run later (as a microtask), never immediately in the same synchronous block.
- **Promise states:** pending → fulfilled/rejected (as covered in Section 1).
- **Promise settlement:** Once fulfilled or rejected, a Promise is "settled" and its state/value is locked forever.
- **Returning a Promise from `.then()`:** If a `.then()` callback returns another Promise, the chain "flattens" — it waits for that inner Promise before moving to the next `.then()`.
- **Returning plain values from `.then()`:** The next `.then()` receives that value directly (wrapped automatically in a resolved Promise).
- **Error propagation:** If an error is thrown anywhere in a chain (or a Promise rejects), it skips all remaining `.then()` calls and jumps to the nearest `.catch()`.
- **Multiple `.then()` on the same Promise:** You can attach multiple independent `.then()` handlers to the same Promise — they all run when it settles, but each doesn't affect the others.
- **Promise chaining:** Each `.then()` returns a brand-new Promise, enabling sequential composition (Section 7).

## 15. Internal Working — How JavaScript Executes a Promise

```js
fetch("/api/users")
    .then(response => response.json())
    .catch(error => console.log(error));
```

### The Key Players

| Component | Role |
|---|---|
| **JavaScript Engine** (e.g., V8) | Runs your JS code — executes the call stack. |
| **Call Stack** | Where currently-executing function calls live, one on top of another. |
| **Web APIs / Browser APIs** | Provided by the browser (not the JS engine) — handle things like `fetch`, `setTimeout`, DOM events. This is where the ACTUAL async work (network request) happens. |
| **Microtask Queue** | Holds Promise callbacks (`.then`, `.catch`, `.finally`) waiting to run. Has HIGHER priority than the Callback Queue. |
| **Callback Queue / Task Queue** | Holds callbacks from things like `setTimeout`, DOM events — lower priority than microtasks. |
| **Event Loop** | Constantly checks: "Is the call stack empty? If yes, take the next task from the Microtask Queue first, then the Callback Queue." |

### Step-by-Step Execution Flow

1. `fetch("/api/users")` is called. This is handed off to the **Web API** environment (the browser handles the actual network request outside the JS engine).
2. The call stack is now free — `fetch` doesn't block anything. JS moves on to the next line of code (if any).
3. `.then()` and `.catch()` are registered as callbacks, waiting for the Promise to settle.
4. Meanwhile, the browser's Web API completes the network request in the background.
5. When the response arrives, the corresponding `.then()` callback is placed into the **Microtask Queue** (NOT the regular callback queue).
6. The **Event Loop** checks: "Is the call stack currently empty?" If yes, it takes tasks from the Microtask Queue FIRST (before any `setTimeout` callbacks in the Task Queue).
7. The `.then()` callback runs, and if it returns a value or throws, that determines what happens in the next link of the chain (also queued as a microtask).

```
CALL STACK          WEB APIs              MICROTASK QUEUE      TASK QUEUE
   │                    │                        │                 │
fetch() ─────────────► [handles request]         │                 │
   │  (stack cleared)   │                         │                 │
   │                 [response ready] ──────────► [.then callback]  │
   │                                               │                │
Event Loop: stack empty? → run microtasks first → run .then()      │
```

## 16. Important Interview Question

**Q: Why are Promise callbacks executed through the Microtask Queue instead of the Callback/Task Queue?**

**Simple explanation:** Promises need to be handled with HIGHER priority than things like `setTimeout` or UI events, because Promise results are often critical, time-sensitive data (like API responses) that other code depends on. JavaScript's designers created a separate, higher-priority queue — the **Microtask Queue** — specifically for Promises (and a few other things like `queueMicrotask`), ensuring they run as soon as possible after the current synchronous code finishes, before the browser moves on to lower-priority tasks like timers or rendering.

**Small example:**

```js
console.log("1");

setTimeout(() => {
    console.log("2 (macrotask - setTimeout)");
}, 0);

Promise.resolve().then(() => {
    console.log("3 (microtask - Promise)");
});

console.log("4");

// Output order: 1, 4, 3, 2
```

Even though `setTimeout` has a delay of `0`, the Promise's `.then()` still runs BEFORE it, because ALL pending microtasks are always fully drained before the event loop touches the next macrotask (like a `setTimeout` callback).

<details><summary>Answer</summary>

**Output: 1, 5, 3, 4, 2**
Synchronous code (`1`, `5`) runs first. Then ALL microtasks (`3`, `4`) run in order, fully draining the microtask queue. Only then does the macrotask (`setTimeout` → `2`) run.

```js
function asyncFunc() {
    return new Promise((resolve) => {
        console.log("inside executor");
        resolve("done");

asyncFunc().then(result => console.log(result));
console.log("end");
```
<details><summary>Answer</summary>

**Output: start, inside executor, end, done**
The executor function runs SYNCHRONOUSLY and immediately when `new Promise()` is called — that's why "inside executor" appears before "end". But the `.then()` callback is still deferred to the microtask queue, so "done" prints last.

### Question 4
```js
Promise.resolve("first")
    .then(res => {
        console.log(res);
        return "second";
    })
    .then(res => {
        console.log(res);

    })
    .catch(err => console.log("caught:", err.message))
    .then(() => console.log("after catch"));
```
<details><summary>Answer</summary>

**Output: first, second, caught: failed, after catch**
Each `.then()` passes its return value to the next. When an error is thrown, it skips directly to `.catch()`. After `.catch()` handles it, the chain continues normally to the next `.then()` (because `.catch()` returns a resolved Promise unless it re-throws).
</details>

console.log("start");

</details>

## 18. Common Beginner Mistakes

1. **Forgetting to `return` a Promise inside `.then()`**
   ```js
   // WRONG
   getUser().then(user => {
       getOrders(user.id); // missing return!
   }).then(orders => {
       console.log(orders); // undefined, because it didn't wait
   });
   ```
   Always `return` the inner Promise so the chain waits for it.

2. **Incorrect `.then()` chaining** — nesting `.then()` inside another `.then()` instead of chaining flatly. This recreates callback hell inside Promises.

3. **Not using `.catch()`** — leads to unhandled Promise rejections, silent failures, and confusing bugs.

4. **Confusing `resolve()` with `return`** — `resolve()` settles the Promise's value; it does NOT stop the executor function from continuing to run (unlike `return`, which does exit a function). Code after `resolve()` in the executor still executes unless you explicitly `return` too.

5. **Thinking a Promise makes code synchronous** — Promises are still asynchronous. `.then()` callbacks never run immediately in the same synchronous block, even if the Promise resolves instantly.

6. **Thinking `await` blocks the entire JavaScript program** — `await` only pauses the execution of the `async` function it's inside. The rest of the program (other functions, UI events) keeps running normally.

7. **Creating unnecessary nested Promises** — wrapping an already-Promise-returning function inside `new Promise()` again (called the "Promise constructor anti-pattern"). If a function already returns a Promise, just return/use it directly instead of re-wrapping it.

## 20. How to Explain a Promise in an Interview

### 60-Second Answer

"A Promise in JavaScript is basically an object that represents a value we don't have yet, but expect to get in the future — usually from something like an API call. Since JavaScript is single-threaded, it can't just pause and wait for slow operations like network requests, or the whole page would freeze. So instead, we kick off the operation, and JavaScript hands us a Promise as a placeholder. That Promise starts in a 'pending' state. Once the operation finishes, it either becomes 'fulfilled' — meaning we got the data — or 'rejected' — meaning something went wrong. We use `.then()` to handle the success case and `.catch()` to handle errors. Promises were introduced mainly to solve callback hell — the deeply nested, hard-to-read code we used to write before Promises existed. They let us write asynchronous code that reads almost like synchronous code, especially when combined with async/await, which is just a cleaner syntax built on top of Promises."

### 2-Minute Detailed Answer

"A Promise is a JavaScript object that represents the eventual result of an asynchronous operation — something that will complete later, not immediately. It has three states: pending, while the operation is still running; fulfilled, when it completes successfully; and rejected, when it fails. Once a Promise settles into fulfilled or rejected, that state is locked — it can never change again.

The reason Promises exist goes back to how JavaScript works. It's single-threaded, meaning it can only execute one thing at a time. If we had operations like network requests or file reads that blocked the thread until they finished, the entire application — including the UI — would freeze. So JavaScript needed a way to start these operations, continue doing other work, and get notified later when the result was ready. Before Promises, this was done using callback functions, but when you had multiple dependent async steps, you'd end up nesting callbacks inside callbacks — this is known as callback hell. It made code hard to read, hard to debug, and painful to handle errors in, because you needed separate error handling at every level.

Promises solved this by letting us chain operations using `.then()`, where each step returns a new Promise, keeping the code flat instead of deeply nested. We also get a single `.catch()` at the end of the chain that can catch an error from ANY step above it, which is much cleaner than callback-based error handling.

On top of this, JavaScript gives us useful static methods like `Promise.all()` to run multiple Promises in parallel and wait for all of them, `Promise.race()` to get whichever settles first, and `Promise.allSettled()` when we want results from everything regardless of failures.

Finally, `async/await` was introduced as syntax sugar on top of Promises — it doesn't replace them, it just lets us write Promise-based code that looks synchronous, using `try/catch` for error handling instead of `.catch()`. Internally, an `async` function still returns a Promise, and `await` still waits on that Promise — it's just a more readable way to work with the same underlying mechanism."

## Revision Cheat Sheet

**States:** Pending → Fulfilled (resolve) / Rejected (reject) — settles once, never changes again.

**Create a Promise:**
```js
new Promise((resolve, reject) => { ... });
```

**Consume a Promise:**
```js
promise.then(onSuccess).catch(onError).finally(onAlways);
```

**Chaining:** Each `.then()` returns a new Promise → return values/Promises flow to the next `.then()`.

**Async/Await:** Syntax sugar over Promises.
```js
async function fn() {
  try {
    const data = await somePromise();
  } catch (e) { ... }
}
```

**Static methods:**
- `Promise.all()` — waits for all, fails fast on first rejection.
- `Promise.allSettled()` — waits for all, never fails, returns status for each.
- `Promise.race()` — first to settle (success or failure) wins.
- `Promise.any()` — first to succeed wins; fails only if ALL fail.
- `Promise.resolve()` / `Promise.reject()` — instantly settled Promises.

**Event Loop priority:** Call Stack → (when empty) drain ALL Microtask Queue (Promises) → THEN one Macrotask (setTimeout, etc.) → repeat.

**Common mistakes:** forgetting `return`, nested `.then()`, no `.catch()`, thinking `await` blocks everything, unnecessary `new Promise()` wrapping.

**One-line interview answer:** "A Promise represents a future value from an async operation — pending until it resolves (success) or rejects (failure), and we handle those outcomes with `.then()`/`.catch()`, or more cleanly with `async/await`."
